# Clean architecture on NestJS-native DI

We adopt the layering and dependency rule of `clean-architecture-guidelines.md` (domain ← application ← infrastructure, ports in `domain/interfaces`, one use case per operation, presenters, domain errors translated to HTTP by an exception filter) but deliberately deviate from its mechanisms: use cases and adapters are `@Injectable()` classes wired by NestJS modules with injection tokens, not curried functions resolved from an ioctopus `di/` container; HTTP input is validated by class-validator DTOs in infrastructure, not Zod in controllers; tests are co-located `.spec.ts` files, not a mirrored `tests/unit/` tree; and the dependency rule is enforced with oxlint's `no-restricted-imports`, not `eslint-plugin-boundaries`, because this repo lints with oxlint. Staying decorator-free only pays off on runtimes without reflection, which this API doesn't target, and class-validator and co-located specs were already in place.
